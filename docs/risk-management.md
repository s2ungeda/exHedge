# 리스크 관리 로직 점검

> TrdBot 집행 엔진의 리스크 가드 4가지에 대한 동작·경우의 수·점검 결과.
> 작성 기준: 현재 소스(`src/trdbot/executor.py`, `app.py`, `broker_ls.py`, `src/lsapi/market_state.py`, `client.py`).
> 이 문서는 **점검·검토용** — 코드 변경은 아직 반영하지 않았다.

대상:
1. 최대잔고한도
2. 체결감시(분)·체결량한도 (체결량 서킷 브레이커)
3. 장운영시간 게이트
4. 주문거부 처리

---

## 1. 최대잔고한도 (`max_position`)

### 로직
새 주문이 **① 절대 포지션을 늘리고 ② 그 결과가 한도를 넘을 때만** 차단(skip)한다.
줄이는(청산) 방향은 한도를 넘어도 **항상 허용**한다. (`executor.py` `reconcile_plan`)

```python
new_pos = effective + signed          # effective = 포지션 + 유지중 미체결
if abs(new_pos) > abs(effective) and abs(new_pos) > max_position:
    skip("최대잔고한도 초과")
```

- `effective`(실효포지션) = 현재 포지션 + 유지 중인 미체결 → 이중주문으로 한도를 넘기지 않음.
- 판정은 **순포지션 절댓값** 기준(원달러선물 최근월+차근월 합).

### 경우의 수 (한도 = 100 예시)

| # | 실효포지션 | 주문 | 새 포지션 | 판정 |
|---|---|---|---|---|
| A | +90 | 매수 +5 | +95 | 주문 (95 ≤ 100) |
| B | +98 | 매수 +5 | +103 | **차단** (늘림 & 103 > 100) |
| C | +100 | 매수 +5 | +105 | **차단** (한도 도달, 증가 불가) |
| D | +100 | 매도 −5 | +95 | 주문 (줄임 → 항상 허용) |
| E | +120 (이미 초과) | 매도 −5 | +115 | 주문 (청산 방향 허용) |
| F | +120 (이미 초과) | 매수 +5 | +125 | **차단** (증가 불가) |
| G | +3 | 매도 −5 | −2 | 주문 (\|2\| < \|3\|, 줄임) |

### 점검 — 주의점
- **(A) 한도는 "더 늘리지 마"지 "한도 안으로 끌어내려"가 아님.**
  실행 중 한도를 낮춰도 이미 초과된 포지션은 **자동 청산되지 않는다.** 포지션은 오직 **목표계약수**를 향해서만 움직이고, 한도는 그 과정에서 증가만 막는다.
  예: 포지션 100·목표 100인데 한도를 50으로 낮춤 → 목표가 100이라 그대로 100 유지(수렴).
- **(B) 1회주문계약수 단위로 한도 아래에서 멈춤.**
  한도 100·포지션 98·1회 5계약 → 103이 되어 차단 → **98에서 정지**(99,100 못 채움). 절대 넘지 않는 대신 한도 근처를 못 채운다(보수적·안전).

### 왜 청산 방향은 한도를 넘어도 허용하나 (설계 근거)
차단 조건은 `abs(new_pos) > abs(effective)`(노출 증가) **와** `abs(new_pos) > max_position`(한도 초과)가 **둘 다** 참일 때뿐이다. 줄이는 주문은 앞 조건이 거짓이라 한도 검사를 아예 타지 않는다. 이렇게 정한 이유:

1. **한도의 목적이 "노출 제한"이다.** 청산은 노출을 줄이는 행위라 막을 이유가 없다(취지와 반대).
2. **초과 상태에서 빠져나올 수 있어야 한다(트랩 방지).** 청산까지 막으면 한 번 한도를 넘는 순간 늘리지도 줄이지도 못하는 데드락에 빠진다. → "줄이는 방향은 항상 허용"이 필수.
3. **초과는 정상적으로 발생 가능하다.** 실행 중 한도를 낮춤 / 부분체결·통보지연·경합 / 목표 이동 → 모두 필요한 동작은 감축.
4. **방향은 목표계약수가 정한다.** 목표가 현재보다 작으면 청산이 곧 원하는 동작 — 한도가 이를 막으면 시그널을 못 따라가고 노출이 그대로 남는다.

요약: **한도 = "더 늘리지 마" 상한선**(증가 방향 브레이크), **청산 = 리스크 감소**라 언제나 허용. 그래서 "한도를 낮춰도 자동 청산은 안 함" 특성과 연결된다 — 실제 감축은 **목표계약수**가 시켜야 일어난다. 한도를 강제청산 트리거로도 쓰려면 별도 기능이 필요하다.
관련 테스트: `test_최대잔고한도_초과면_skip`(증가 차단), `test_포지션초과시_반대주문_및_같은방향취소`(초과 시 감축 허용).

## 2. 체결감시(분)·체결량한도 (체결량 서킷 브레이커)

### 로직
최근 `감시시간` 안 + **재개 시점 이후** 누적 **체결량**이 `한도` 이상이면 트립 →
**미체결 전부 취소 + '주문' 자동 해제(latch)**. 사용자가 '주문'을 다시 체크해야 재개.

- 판정 (`app.py` `_fill_breaker`): `recent_fill_qty(fills, now, window, since=재개시각) >= fill_limit`
- 트립 동작 (`executor.py` `reconcile`): 미체결 취소 → `on_breaker_trip` → `trade_enabled=False`
- 재개 (`app.py` `_on_trade_toggle`): '주문' 체크 시 `_breaker_reset_at = now` → 카운트 리셋
- `fill_limit = 0` → 기능 끔.
- 체결량은 **체결 통보(C01/C02)** 기준. 주문 수가 아니라 실제 체결 수량.

### 경우의 수

| # | 한도 | 감시시간 | 누적 체결량 | 판정 |
|---|---|---|---|---|
| A | 0 | — | — | 기능 끔 (항상 통과) |
| B | 20 | 10분 | 15 (< 20) | 정상 주문 |
| C | 20 | 10분 | 20 (≥ 20) | **트립**: 미체결 취소 + 주문 중지 |
| D | 20 | 10분 | 트립 후 '주문' 재체크 | 재개, 카운트 0부터 |
| E | 20 | 10분 | 옛 체결이 10분 밖으로 | 그만큼 카운트에서 빠짐(자연 감소) |
| F | 20 | **0분** | 무엇이든 | **기능 끔** ← 주의 |

### 점검 — 주의점
- **(A) 감시시간 0분 = 브레이커 무력화(함정).**
  `recent_fill_qty`는 `window_sec <= 0`이면 무조건 0을 반환한다. 한도를 20으로 걸어도 **감시시간이 0이면 절대 안 걸린다.** UI에서 실수로 0을 두면 리스크 가드가 조용히 꺼진다.
- **(B) 재개 시 카운트 완전 리셋(쿨다운 없음).**
  트립 후 '주문'을 바로 다시 체크하면 카운트가 0으로 리셋돼 즉시 재개된다. 같은 폭주 상황이면 `한도`만큼 더 체결된 뒤 다시 트립. **수동 확인이 유일한 브레이크**이고 자동 대기시간은 없다.

## 3. 장운영시간 게이트 (`in_window`)

### 로직
주문 가능 여부를 **3단 게이트**로 판정한다 (`app.py` `_in_session_window`). 모든 단을 통과해야 주문이 나가고, 하나라도 막히면 `skip("주문가능시간 외")`.

```
1차: session_now(시각) → day / night / closed        (closed면 즉시 차단)
2차: 사용자 주간/야간 시간창 안에 있나                (밖이면 차단)
3차: JIF 실시간 장운영 국면                            (있으면 이게 진실)
     └ JIF 미수신이면 → 시각 기반 폴백 국면
```

**JIF(장운영데이터)** = LS OpenAPI 실시간 "장운영정보" TR. `tr_key="0"`으로 한 번 구독하면 모든 시장의 장상태 전이(장시작·동시호가·서킷브레이크·마감 등)를 이벤트로 흘려준다 — 봇이 지금 장 국면을 실시간으로 아는 근거.

**국면(Phase) 판정** (`market_state.py`): **접속매매(CONTINUOUS)에서만** 주문 허용.
동시호가·서킷브레이크·마감은 전부 금지. JIF는 **엣지 트리거**(상태가 바뀔 때만 1건 수신) → 마지막 이벤트로 현재 국면을 유지한다.

### 미국달러선물 장운영 시각 (기준)

| 구분 | 시각(한국) | 국면 | 봇 처리 |
|---|---|---|---|
| 주간 장개시 동시호가 | ~08:45 이전 | 단일가 | `closed` 세션 → 주문 금지 |
| **주간 접속매매** | **08:45 ~ 15:35** | 연속 | **거래 가능** |
| 주간 장마감 동시호가 | 15:35 ~ 15:45 | 단일가 | 주문 금지 |
| 야간 시가 단일가 | 17:50 ~ 18:00 | 단일가 | `closed` 세션 → 주문 금지 |
| **야간 접속매매** | **18:00 ~ 05:50(익일)** | 연속 | **거래 가능** |
| 야간 종가 단일가 | 05:50 ~ 06:00 | 단일가 | 주문 금지 |

**코드 상수 대응**
- `session_now` (`futures.py`): 주간 `08:45~15:45` → day, 야간 `18:00~06:00` → night, 그 외 closed.
- `current_time_phase` 폴백 상수 (`market_state.py`): `DAY_OPEN_AUCTION_END=845`(접속매매 시작), `DAY_CLOSE_AUCTION_START=1535`(마감 동시호가 시작), `NIGHT_CLOSE_AUCTION_START=550`(야간 종가단일가 시작).

> ✅ **정합성 반영됨(2026-08-04)**: 예전엔 폴백 `DAY_OPEN_AUCTION_END`가 **09:00**이라 `session_now`(08:45)와 어긋나 **JIF 미수신 시 08:45~09:00을 동시호가로 오판 → 주문 차단**되던 버그가 있었다. → **08:45로 맞춤**. (JIF 수신 중이면 실시간 국면이 우선)

### 일일 리셋(토큰 재발급 · WS 재연결) 시각

LS access 토큰은 밤사이 무효화되므로, **하루 1회 개장 전에 선제 재발급 + WS 재연결**한다 (`app.py` `_ensure_daily_token`).

| 항목 | 값 |
|---|---|
| **리셋 시각** | **08:30**(프리마켓, 개장 08:45 전) ~ 15:45 사이 **첫 틱에 1회** |
| 하는 일 | REST 토큰 `force_refresh` + WS(시세·장운영·체결) 재연결·재구독 |
| 트리거 | `830 <= 현재HHMM <= 1545` 이고 그날 아직 안 했으면 |
| 로그 | `장 개시 전(프리마켓) — 토큰 선제 재발급 완료` / `... WS 재연결(재구독) 요청` |

> ⚠️ **왜 개장(08:45)이 아니라 08:30인가 (2026-08-04 수정)**: 예전엔 `session_now=="day"`(08:45)에 트리거돼 **개장 순간에 재연결**했다. 그 순간 JIF가 막 보낸 개장(접속매매) 이벤트와 재연결이 경쟁 → **개장 국면을 놓쳐 08:45~09:00 주문 차단**(실측 2026-08-04 오전). → **개장 전 08:30**으로 옮겨, 개장 때는 이미 안정 연결 상태가 되게 함. (추가로 "의도된 재연결에는 JIF 국면 리셋 안 함"도 반영)

### 경우의 수

> **"시간창"** = 사용자가 화면에 설정한 **주간/야간 주문가능시간**(예 주간 08:00~15:45).
> **창 안** = 현재 시각이 그 범위 안 · **창 밖** = 범위 밖(→ 주문 차단). JIF 국면(접속매매 등)과는 별개의 판정이다.

| # | 세션(시각) | 사용자 시간창 | JIF 국면 | 판정 |
|---|---|---|---|---|
| A | closed | — | — | 금지 (1차 차단) |
| B | day/night | 창 밖 | — | 금지 (2차 차단) |
| C | day/night | 창 안 | 접속매매 | 주문 가능 |
| D | day/night | 창 안 | 동시호가/서킷/마감 | 금지 (JIF 우선) |
| E | day/night | 창 안 | JIF 미수신 + 폴백 접속매매 | 주문 가능 |
| F | day/night | 창 안 | JIF 미수신 + 폴백 동시호가(장개시·장마감·야간종가단일가) | 금지 |

### 점검 — 주의점
- **(A) JIF 놓친 전이 방어 — ✅ 반영됨.**
  장운영(JIF) WS가 끊기면 `on_disconnect` 콜백이 `MarketStateTracker.reset()`을 호출해 **저장된 국면을 비운다** → `seen()=False`가 되어 **시각 기반 폴백으로 전환**한다. 다음 JIF 이벤트가 올 때까지는 시각 국면으로 판단하므로, stale한 접속매매 국면으로 서킷브레이크·동시호가를 못 거르는 문제를 막는다. (재연결 후 첫 JIF 전이가 오면 다시 실시간 국면 사용)
- **(B) 이중 방어는 잘 돼 있음.**
  session_now(시각) + 사용자 시간창이 항상 겹겹으로 걸어서, 국면 판정이 틀려도 세션 시각 밖이면 결국 막힌다.

## 4. 주문거부 처리

### 로직
`place_order`가 **거부 시 예외를 던지고**, 집행 루프가 그걸 잡아 다음 사이클에 재시도한다.

```
api.place_order → client._request 응답코드 판정
   비-00000 & OutBlock 없음 → LSAPIError raise   (예: 01407 매매불가)
   IGW*  → LSAuthError (토큰 1회 재발급 재시도 후에도 실패면)
   IGW00201 / 429 → 3회 백오프 재시도 후 LSRateLimitError
 ↓ broker.place_order: OrdNo 없으면 RuntimeError "주문번호 없음"
 ↓ executor.reconcile(): place_order에 try/except 없음 → 예외 전파
 ↓ executor.run(): 사이클 전체를 try/except로 잡음
   → logger.exception("집행 사이클 예외")  [파일 로그만]  → idle_wait → 다음 사이클 재시도
```

응답코드 규약(모의 실측): `00000`=조회 정상, 주문류는 비-00000 성공코드(예 `00040` 매수접수 / `00156` 취소완료)에 OutBlock 동봉. 실패는 rsp_cd/rsp_msg만 오고 OutBlock 없음(예 `01407` 매매불가) → 그때만 에러로 raise.

### 경우의 수

| # | 상황 | API 결과 | 봇 동작 |
|---|---|---|---|
| A | 정상 접수 | 00040 등 + OutBlock + OrdNo | 주문번호 등록, 추적 |
| B | 매매불가/거부 | 01407 등 (OutBlock 없음) | LSAPIError → 캐치 → **파일로그** → 재시도 |
| C | OrdNo 누락 | OutBlock 있으나 번호 없음 | RuntimeError → 캐치 → 재시도 |
| D | 인증오류 | IGW00121 등 | 토큰 재발급 1회 후 실패 시 LSAuthError → 재시도 |
| E | 레이트리밋 | IGW00201 / 429 | client가 3회 백오프 후 실패 시 → 재시도 |
| F | 네트워크/HTTP | 타임아웃·5xx | LSAPIError → 재시도 |

### 점검 — 주의점
- **(A) 거부 화면 표시 — ✅ 반영됨.**
  `place_order` 예외를 reconcile에서 잡아 `⚠ 주문거부: {사유}`를 **화면 상태줄에 표시**한다(과거엔 파일 로그만).
- **(B) 지속 거부 백오프 — ✅ 반영됨.**
  연속 거부마다 재시도 간격을 **지수 백오프**(1→2→4→8…초, 상한 30초)로 늘린다. 성공하면 0으로 리셋. 백오프 중에는 새 시그널로 안 깨어나 재시도 스팸을 막고, 중지에는 즉시 반응. (참고: `latch`(자동 중지) 대신 **백오프만** 적용 — 일시적 원인이 풀리면 자동 회복)
- **(C) 부분 상태 손상은 경미.**
  `place_order`는 사이클의 마지막 단계라, 거부로 사이클이 중단돼도 포지션 갱신 등 앞 처리엔 영향이 없다.
